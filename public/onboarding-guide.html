OverviewHigh-Level Onboarding Flow

Record 1: owner_context_doc Custom

The company knowledge base read by AI Planner and Campaign Creator. Must cover:

  • Who we are (mission, core belief, differentiation)
  • Target market (industries, company sizes, decision-maker titles)
  • Value propositions (one-liners + role-specific value)
  • Service offerings and pricing
  • Case studies (anonymized: industry, result, key insight)
  • Key metrics and proof points
  • Objection handling (common objections + responses)
  • Tone and style guide (how the company communicates)

Record 2: system_defaults Custom

The AI operating constitution. Copy from system_defaults_template, then customize three sections:

  • Section 4 -- Role Registry: HITL reviewer name, email, Slack handle, SLA, availability
  • Section 8 -- Sending Identity: Sender email, display name, title, Secrets Manager alias
  • Section 11 -- Pipeline Stage Index: All stages with description, entry/exit criteria, authority level

All other sections (authority levels, task matrix, timing, reply classification, etc.) are copied verbatim.

Records 3-6: Template Records Pre-populated

KeyPurposeEdit?

outreach_plan_template8-section structure for AI outreach plansNever
campaign_plan_template16-section campaign constitution templateNever

Record 7: tone_style_guide_{sender_email} Post-OAuth

Key format: tone_style_guide_jane@acme.com. Generated from real sent emails after OAuth is confirmed. One record per sender. Covers tone, typical length/structure, greetings, CTAs, patterns to preserve and avoid.

Tip: Using NotebookLM to Generate Config Content

The owner_context_doc and system_defaults records require deep company knowledge. An efficient approach:

  1. Create a Google NotebookLM notebook and upload all past sales calls, discovery recordings, and company materials.
  2. Export the Config record templates from the Airtable template base (appUPjXzr45sFr79j) -- specifically the system_defaults_template, outreach_plan_template, and campaign_plan_template Values.
  3. Feed those templates to NotebookLM and ask it to fill them based on the uploaded source material.
  4. Review and refine the output with the customer before pasting into Airtable Config records.

This approach produces higher-quality, more authentic config content than manual interviews alone, especially for the owner context doc and tone/style profiles.

1.5 MCP Lambda Configuration

The MCP Lambdas are shared across all customers. To add a new customer, update the config in the bb-mcp repo.

File: bb-mcp/packages/airtable-bb-os/cdk/config/prod.json

Add a new entry to the customers object:

"customers": {
  "brain-bridge": {
    "base_id": "appwzoLR6BDTeSfyS",
    "secret_name": "bb-os-mcp-at/api-key"
  },
  "{new-slug}": {
    "base_id": "{new-base-id}",            // From Airtable clone
    "secret_name": "bb-os-mcp-at/{slug}/prod/api-key"
  }
}

Then redeploy the MCP stack: cd bb-mcp/packages/airtable-bb-os/cdk && cdk deploy

!
Important: MCP Lambdas have a 1-hour in-memory schema cache per Lambda. After adding a new customer, force cold starts by updating each Lambda's description (NOT env vars -- that wipes all config).

Gmail

Setup:

  1. Create OAuth 2.0 Client in Google Cloud Console
  2. Enable Gmail API
  3. Add redirect URI (from CDK output, post-deploy)
  4. Create .env.{slug}-{env} file with GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET
  5. Source the .env file before CDK deploy

Scopes needed: gmail.send, gmail.readonly

OAuth URL: https://gmail.auth.brainbridgelabs.ai/oauth/start

Credential storage: OAuth Lambda auto-writes to Secrets Manager after sender authenticates.

Outlook / Microsoft 365

Setup:

  1. Register app in Azure Active Directory
  2. Add delegated permissions: Mail.Send, Mail.Read, offline_access, User.Read
  3. Grant admin consent (requires Global Admin)
  4. Create client secret (24-month expiry recommended)
  5. Add redirect URI from CDK output

Credential storage: Create placeholder secret pre-deploy; OAuth Lambda updates with real tokens after sender authenticates.

i
For Gmail customers: You need a .env.{slug}-{env} file in the project root with GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. Source it before CDK deploy: set -a && source .env.{slug}-{env} && set +a

2.3 Email OAuth Flow

After the first CDK deploy creates the OAuth endpoints, the sender authenticates via browser. The Lambda handles the full token exchange and writes credentials to Secrets Manager automatically.

sequenceDiagram
    participant Admin as Admin
    participant Sender as Email Sender
    participant APIGW as API Gateway
    participant Lambda as OAuth Lambda
    participant Provider as Google / Microsoft
    participant SM as Secrets Manager

    Admin->>Sender: Share OAuth URL
    Sender->>APIGW: gmail.auth.brainbridgelabs.ai/oauth/start
    APIGW->>Lambda: Invoke
    Lambda-->>Sender: Redirect to provider consent
    Sender->>Provider: Authenticate + consent
    Provider-->>APIGW: Redirect with auth code
    APIGW->>Lambda: GET /oauth/callback?code=...
    Lambda->>Provider: Exchange code for tokens
    Provider-->>Lambda: access_token + refresh_token
    Lambda->>SM: Store credentials
    Lambda-->>Sender: Success page
